Executive verdict

质量打平，Codex 明显更省时间与工具轮次；Luban 费用略低

官方严格主分：Codex 2/5，Luban 2/5。五题逐题结果完全一致，因此本样本没有显示任何质量领先者。两者在 Skim 的核心生产代码都正确，但都因新增测试与官方隐藏测试同名而被严格判失败；对称的生产代码诊断复评后，两者均相当于 3/5，仍打平。

效率差异更清晰：Codex 总 Agent 时间少 26.9%，工具调用少 59.3%；Luban 的估算模型费低 5.4%。这说明相同模型下，真正拉开差距的是上下文组织、工具接口和行动策略，而非本次可观察到的修复成功率。

不能外推为总体排行榜。 只有 5 题、每题单次运行；2/5 的 95% Wilson 区间对两端都是 11.8%–76.9%。当前结论适合做工程选型信号，不适合宣称统计显著的能力胜负。

方法与公平控制

固定条件

  • Codex codex-cli 0.144.6；Luban luban-code v0.1.0，源码提交 7a8e62b317b632e0e11ed1f32ef660a20369678c。
  • 两端精确模型 ID 均为 gpt-5.6-sol，reasoning effort 均为 xhigh，走同一 OpenAI-compatible endpoint。Luban provider debug 请求逐次记录了两字段；Codex 通过 CLI 显式覆盖并忽略用户配置。
  • 每题使用相同 issue 文本、相同 base commit、独立浅克隆；remote 被移除，禁止网络、Web、子 Agent、远端历史及提交。
  • 每次单轮 pass@1，Agent 硬上限 1800 秒；执行顺序交错，降低先后顺序偏差。

题目与评分

  • 来源是 SWE-bench-Live MultiLang，固定 Hugging Face revision 608f7ae9ab8e…，而非滚动 latest。
  • 正式五题覆盖 5 个项目、4 种语言和 API/生命周期、配置兼容、CLI 选项、静态分析器语义；所有题先用 gold patch 通过完整评分集合。
  • 评分复现 官方 SWE-bench-Live / RepoLaunch 的 test patch、rebuild/test/print commands 与随题 log parser；resolved 要求全部 F2P 与 P2P 通过。
  • 没有采用 SWE-bench Pro 作为主集：OpenAI 公开审计报告其中约 30% 题目存在严重问题，pilot 更适合用新鲜且带可执行容器的 Live 快照。

费用公式

(未缓存输入 × $5 + 缓存输入 × $0.50 + 输出 × $30) / 1,000,000。单价固定自本仓库模型目录 catalog_sync.py 与 pricing.go；这是基于 Agent token 事件的可比估算，不是 endpoint 账单。正式五题共 $16.1292；被排除 WXT 两次运行 $2.1069；所有已记录 Agent 运行合计 $18.2361。未货币化本机算力、镜像网络与评测 VM。

执行环境

macOS 15.4.1 (24E263), arm64；官方镜像在 Lima Debian Linux x86_64, 4 vCPU, 3.8 GiB RAM, no swap, 40 GiB disk 上以 rootless nerdctl 运行。Agent 工作区在主机，评分工作区在隔离 Linux 容器。

异常、排除与替补

这里完整披露筛题过程。尤其 WXT 是在 Agent 运行后才排除，属于 post-hoc 决策，存在选择偏差风险；保留其全部成本与轨迹，便于读者自行做敏感性分析。

安全事件：Fabric / Luban 工具输出捕获宿主凭据

当时运行器把完整宿主环境传给两端进程；在 Fabric 轨迹中，Luban 明确执行了 env，使 API、Git、包仓库和发布类凭据进入工具结果，并随上下文发送到配置的模型端点。交付前已从全部文本工件识别并全局替换 12 个不同敏感值，共修改 18 个文件；二次扫描四类模式均为 0。脱敏不能撤销此前的端点传输，建议轮换当时环境中的相关凭据。交付版运行器已改为环境 allowlist，只保留基础运行变量与模型认证变量。脱敏脚本

Defuddle / TypeScript：gold 性能阈值失败，未运行 Agent

目标 1/1 通过，但既有 239 项中性能测试 Performance parse time per fixture... 在 4 vCPU VM 失败（238/239）。gold report

WXT / TypeScript：外网型 P2P 波动，整题排除

gold 为 2/2 + 799/799；Codex 2/2 + 799/799，Luban 2/2 + 798/799，唯一失败是远端 url:* 模块下载。两端核心补丁语义相同，故不把网络失败算作 Luban 能力差距。Codex：5m 04.2s / $0.9145 / 14 tools；Luban：12m 00.2s / $1.1924 / 59 tools。gold · Codex · Luban

OpenDataLoader PDF / Java：JDK 在虚拟化 x86_64 上崩溃

gold rebuild 先后出现 Temurin 21 SIGILL/SIGSEGV，目标测试未执行，排除 Java 题；这也是最终语言覆盖为 4 种而非 5 种的原因。gold report

Hugo / Go 与 Biome / Rust：官方镜像拉取超过 1,800 秒

两题都在 gold 之前因镜像拉取硬超时淘汰；没有模型调用。最初的宿主 timeout 未结束 VM 内 Biome pull，发现后按精确 PID 终止，并把评测器改为 VM 内 timeout；该适配器修复不改变 Agent 提示或评分。Hugo 由 kube-state-metrics 替补，Biome 由 Skim 替补。

Skim：官方严格失败与生产代码诊断通过

双方都独立新增了同名 opt_border_none 测试，与官方 test patch 合并后重复定义，官方严格主分必须记失败。对称排除各自 tests/options.rs 后：Codex diagnostic 与 Luban diagnostic 均通过全部评分项；这不回写主分。

如何解读，不应如何解读

  • 样本太小：5 题、每题 1 次；没有估计随机采样方差，也无法证明质量等价。严格分 40%，95% Wilson 区间宽达 11.8%–76.9%。
  • 公开题污染：公开 issue/patch 可能进入训练或检索语料；禁网只能阻止运行时查答案，不能证明模型未见过。
  • 同模型不等于同请求：两款 Agent 的系统提示、工具 schema、上下文压缩和缓存策略不同，正是本实验测量对象；因此 token 不能解释为“模型思考量”的纯指标。
  • 工具次数不是等价单位：Codex 的一条 command 可执行复合操作，Luban 使用更细粒度的 Read/Grep/Edit；总数适合看编排风格，不适合按次给工具定价。
  • 费用是目录价估算：Luban 未返回 reasoning token；输出 token 已包含供应端计费事件中的输出总量。没有账单核对，也不含容器计算、网络或人工时间。
  • gold 门禁只执行一次：官方大规模流程建议多次 gold 运行过滤不稳定题；本 pilot 因资源限制只跑一次，并通过替补和异常披露降低风险。
  • 基础设施限制：arm64 主机上的 x86_64 Lima VM、4GB 内存与 40GB 磁盘导致 Java JIT 崩溃和大镜像慢下载；这影响可选题分布，但正式五题的双方条件相同。
